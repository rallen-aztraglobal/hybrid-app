# ADR-0015: 设备登记表以安装 UUID 为唯一键,受众哈希导出时算不落库

- **状态**:已采纳(2026-08-17)
- **背景**:渠道 APK 要上报 GAID + Adjust ADID(+HMS OAID)供运营导出上传 Meta/TikTok 做设备受众。
  数据量最多百万级。GAID 会因用户关闭广告个性化变成全 0、也可被用户重置;Adjust ADID 首次启动
  归因未完成时为空——两者(及其复合)都不满足「永远非空且稳定」,不能当设备唯一键。
- **决策**:
  1. 客户端生成并持久化**安装 UUID(`device_key`)**作 `channel_device` 表唯一键;
     upsert 按 device_key 合并,标识字段来值非空才覆盖,`created_at`(注册时间)永不覆盖。
  2. **无有效 GAID 不采集**:GAID 为空/全 0(无 GMS、用户 opt-out)时客户端整条不上报,
     服务端同样 400 拒收(双保险);Meta/TikTok 用的 SHA256 **导出时流式计算,不落库**。
     由此华为 OAID 兜底采集也一并取消(它只在无 GAID 时才有意义,而无 GAID 已不上报),
     `oaid` 列保留为空作历史兼容。
  3. 列表用 Count+Offset 分页但 **offset 钳 10 万**、pageSize 钳 200;全量导出不传 id 列表,
     按筛选条件走 `Rows()` 游标流式写 CSV;勾选导出传 id 列表钳 1000。
  4. 全量导出下载走 5 分钟 scope 短 token(query 传递)+ 浏览器原生下载,不用 fetch→Blob。
- **理由**:
  - UUID 语义恰为「一次安装=一台设备」,注册时间=首次上报天然成立;卸载重装算新设备,
    与 Adjust 的安装口径一致,对受众投放无害。
  - 无 GAID 的行对受众上传毫无价值(Meta/TikTok 都以 GAID 为匹配键),留在库里只会
    膨胀数据量、导出后还要人工过滤——不如源头不收。
  - SHA256 不落库:口径归导出层,平台要求变化(MD5/大小写)不用洗百万行数据。
  - offset 钳制:管理后台无深翻页刚需,配合 `(application_id, created_at, id)` 复合索引,
    最坏查询可控,避免为键集分页牺牲「跳页」交互。
  - 百万行 CSV ≈ 200MB,fetch→Blob 在浏览器内存翻倍持有,原生下载直接流到磁盘;
    长效 access token 不能进 URL(浏览器历史/代理日志泄漏),故签短效窄 scope token。
- **后果**:
  - 正面:客户端 24h 节流后写入峰值仅百余 QPS,单机 MySQL 直扛,无队列组件;
    导出服务端内存 O(1)。
  - 负面:同一物理设备重装会产生多行(GAID 相同、device_key 不同),导出上传前平台侧会自动去重,
    Console 列表侧不做去重;深翻页被禁止,只能靠筛选收窄或导出。
  - 跟进:上线后给存量角色手动勾新权限点;若渠道校验点查成为热点,可加 5 分钟 TTL 内存缓存。
- **备选**:
  - GAID 作唯一键:全 0/重置即撞键或串数据,弃。
  - (gaid, adid) 复合键:两者皆可空,唯一约束语义破碎,弃。
  - SHA256 落库:多存一列且口径焊死,弃。
  - 键集分页(cursor):百万级下性能最优,但破坏跳页且前端复杂,管理后台场景收益不值,弃。
  - 导出走 fetch→Blob 统一通道:实现最简,但大文件浏览器内存不可控,仅保留给 ≤1000 行勾选导出。
